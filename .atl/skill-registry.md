## 5. Compact rules

### 5.1 Data & backend

#### supabase
- Verify against `https://supabase.com/changelog.md` and current docs before implementing — never trust training data for signatures or `config.toml` keys.
- Enable RLS on every table in an exposed schema; RLS is *not* table exposure — a SQL-created table may need an explicit `GRANT` to `anon`/`authenticated`.
- Never use `user_metadata` / `raw_user_meta_data` for authorization — it is user-editable. Use `raw_app_meta_data` / `app_metadata`.
- Never expose `service_role` or the secret key in a client. Ship only publishable/anon keys; Astro bundles any public `PUBLIC_*` env var to the browser.
- Views bypass RLS by default — use `CREATE VIEW ... WITH (security_invoker = true)` (PG15+) or revoke access.
- `UPDATE` silently updates 0 rows without a `SELECT` policy; an `UPDATE` policy needs **both** `USING` and `WITH CHECK`.
- `auth.role()` is deprecated — use the `TO authenticated` / `TO anon` clause. `TO authenticated` alone is BOLA/IDOR without an ownership predicate in `USING`.
- `SECURITY DEFINER` bypasses RLS and is callable by `PUBLIC` when in `public` — prefer `SECURITY INVOKER`; never add it to fix a permission error.
- Storage upsert needs `INSERT` + `SELECT` + `UPDATE` grants; `INSERT` alone makes replacement silently fail.
- Pin package versions and commit the lockfile.
- CLI: always discover with `--help`, never guess flags; hand-authored migrations start with `supabase migration new <name>`.
- On any API/Postgres/Auth/Storage error, fetch `https://supabase.com/docs/guides/monitoring-and-debugging.md` before diagnosing. Verify every fix with a real query. Stop after 2-3 failed attempts instead of retrying.

#### supabase-postgres-best-practices
- Load before writing or changing anything in Postgres — including a one-column change or a single query. It is not only a performance guide.
- Work the priority order: `query-` and `conn-` and `security-` are CRITICAL; `schema-` HIGH; `lock-` MEDIUM-HIGH; `data-` MEDIUM; `monitor-` LOW-MEDIUM; `advanced-` LOW.
- Read the specific rule file `references/<prefix>-<rule>.md` for the incorrect-vs-correct SQL — do not invent index or constraint syntax from memory.
- Index against real predicates: partial indexes for soft-delete/status filters, composite indexes ordered by equality-then-range.
- Keep transactions short and avoid long DDL locks on live tables.
- Never widen `SELECT *` in application queries; paginate list endpoints.
- Confirm with `EXPLAIN (ANALYZE, BUFFERS)` before and after an optimization, not by intuition.

### 5.2 Frontend platform (TypeScript, testing)

#### typescript-advanced-types
- `unknown` over `any`; keep `strict` on. Never ship an implicit `any`.
- `interface` for object shapes (better errors); `type` for unions and composition.
- Constrain generics with `extends`; reach for `infer` only inside conditional types.
- Mapped types + `as` key remapping and template-literal types for string unions (e.g. `Line`, `Gender`, `Accord`).
- Prefer type guards over `as` assertions — assertions silence real mismatches.
- Use discriminated unions for cart line state (`compra` | `encargo`) instead of optional flags.
- Add `readonly` where mutation is not intended.
- Type tests: the `AssertEqual` + `ExpectError` pair pattern.
- Avoid deeply nested conditional types — they slow compilation badly.

#### vitest
- Vitest 5.x is Vite-native and Jest-compatible; it reuses `vite.config.ts` transform/resolve/plugins.
- Read the matching `references/<topic>.md` for exact API — do not guess matcher names.
- Modifiers: `test.skip`, `.only`, `.concurrent`; `aroundEach` for wrap-style hooks.
- Mocking via `vi.mock` / `vi.spyOn` / `vi.useFakeTimers` / `vi.hoisted` / `vi.waitFor`.
- Custom fixtures with `test.extend`; access `context.expect`.
- Environments: `node` default; `jsdom` or `happy-dom` for DOM islands; multi-project config for mixed envs.
- Type-level assertions: `expectTypeOf` / `assertType`.
- Coverage from the `v8` (default) or `istanbul` provider.
- Filter with `-t`, path patterns or tags rather than commenting tests out.

### 5.3 Accessibility

#### accessibility
- Evidence first: audit the rendered page (Lighthouse/axe), fix the failing nodes it names, re-run. A score of 100 is **not** WCAG conformance.
- Every `<img>` needs `alt`; decorative images use `alt="" role="presentation"`. Icon-only buttons need `aria-label` and `aria-hidden="true"` on the SVG.
- Contrast: 4.5:1 normal text, 3:1 large text and UI components/graphics. Focus indicators need 3:1 (1.4.11).
- Never `outline: none` without a `:focus-visible` replacement (2px solid + offset).
- Prefer native elements; only add `role`/`tabindex`/keydown when a native element is impossible — and never on a native `<button>` (double-trigger).
- Target size ≥ 24×24 CSS px (AA); 44×44 recommended for the two non-technical admins.
- Every input needs a programmatic label; errors use `aria-invalid="true"` + `aria-describedby` + `role="alert"`, and focus the first error on submit.
- Never signal state with color alone — pair with icon or text (critical for "En stock" / "Sin stock, por encargo").
- Honor `prefers-reduced-motion`; keep content usable at 200% zoom.
- Set `<html lang>`, use ordered headings, provide a skip link, no keyboard traps.
- WCAG 2.2 additions to check: focus not obscured by sticky bars (`scroll-margin-top`), no redundant entry, accessible auth (allow paste + autofill in the admin login).

### 5.4 UI craft

#### emil-design-eng
- Animate only `transform` and `opacity` — never `width`, `height`, `padding`, `margin`, `top`, `left`.
- Frequency decides motion: 100+/day → no animation ever; tens/day → reduce drastically; occasional (modals, toasts) → standard; rare → delight. Never animate keyboard-initiated actions.
- Durations: 150–250ms for UI, never > 300ms. Exit faster than enter.
- Easing: `ease-out` for enter/exit, `ease-in-out` for on-screen movement, `linear` only for constant motion. **Never `ease-in`** for UI.
- Use a strong custom curve, not the weak built-in: `cubic-bezier(0.23, 1, 0.32, 1)`.
- Never enter from `scale(0)` — start at `scale(0.95)` + `opacity: 0`.
- Never `transition: all` — name the exact properties.
- Prefer CSS transitions over keyframes for interruptible UI; use WAAPI for programmatic CSS motion.
- Popovers get `transform-origin` at the trigger; modals stay centered.
- Wrap hover-only effects in `@media (hover: hover) and (pointer: fine)`.
- Stagger 30–80ms between list items. Framer Motion `x`/`y`/`scale` shorthands are main-thread — use the full `transform` string when it must stay smooth under load.

#### design-taste-frontend-v1
- Baseline dials are 8 / 6 / 4 (DESIGN_VARIANCE / MOTION_INTENSITY / VISUAL_DENSITY); honor explicit user overrides.
- Verify every third-party import against `package.json` first, and emit the install command when it is missing.
- Animate `transform` + `opacity` only — never `top`, `left`, `width`, `height`. Use z-index only for systemic layers.
- No emojis anywhere in code, markup, content or alt text — icons or clean SVG.
- Full-height sections use `min-h-[100dvh]`, never `h-screen` (iOS Safari jump).
- CSS Grid over flex-percentage math; any asymmetric desktop layout must collapse to a strict single column below `md:`.
- Ship full interaction cycles: loading skeletons sized to the layout, composed empty states, inline errors, `:active` tactile feedback.
- Form labels sit above the input; error text below; consistent input-block gap.
- Forbidden AI tells: pure `#000000`, neon/outer glows, `Inter`, the 3-equal-cards row, gradient text headers, custom cursors, "John Doe" placeholder data, filler copy ("Elevate", "Seamless").
- **CONFLICT — this project:** the "lila/purple ban" contradicts the approved `#CC7BCA` / `#F0BBEA` identity. The design system wins.
- **CONFLICT — this project:** the skill assumes React/Next RSC + Tailwind + Framer Motion. Here it is Astro static + React islands; ignore RSC, `'use client'` and Tailwind-version rules unless the island actually uses them.

### 5.5 OpenSpec workflow

#### openspec-propose
- **Planning only.** The request that invoked this authorizes planning, never code edits — create the artifacts, stop, and wait for a new request before applying.
- Confirm the root first (`openspec list --json` / `openspec context --json`). `root: null` is an answer, not a broken CLI — do not retry or work around it.
- Never run `openspec init` or hand-create `openspec/` unless the user explicitly asks.
- Always `openspec new change "<kebab-name>"` — never scaffold a directory under `openspec/changes/` by hand.
- Build the whole transitive required set (`applyRequires` plus every artifact reachable through `requires`), not only the ids in `apply.requires`.
- `status` is file-existence only: a `done` artifact can still have missing dependencies — follow `requires` edges.
- Re-read dependency artifacts from disk before drafting each new one.
- `context` / `rules` / `template` from `openspec instructions` are constraints on you — never copy them into the artifact.
- An artifact reporting `skipped` must NOT exist; only skip when status says skipped or its `instruction` marks it conditional.
- Verify each artifact file exists after writing. Ask about ambiguities that change scope or acceptance criteria; assume and record the minor ones.
- If a registered store is selected, keep `--store <id>` on every subsequent OpenSpec command.

#### openspec-apply-change
- Read every path in `contextFiles` from the apply instructions before touching code.
- Loop: implement the task, flip `- [ ]` → `- [x]` at the returned `sourcePath` and `line`, continue.
- Only check a task off when its specified behavior is fully implemented — never when partially done or deferred.
- `state: blocked` → stop. If `missingArtifacts` is non-empty, complete those first; never implement while blocked.
- Never silently narrow, defer or drop specified behavior to make it fit — surface the added scope and ask.
- Keep changes minimal and scoped to the current task.
- Pause on ambiguity, on a design issue revealed by implementation, or on an error — do not guess.
- `context` is required input; `operationGuidance` is advisory. On conflict, report it and keep the controlling value.
- `all_done` → report completion and suggest archive.

#### openspec-update-change
- Planning artifacts only — **never** edit implementation code. A plan that implies code changes goes to `/opsx-apply`.
- Edit only the concrete files in `artifactPaths.<id>.existingOutputPaths`; never write to the glob `resolvedOutputPath`.
- Never create missing artifacts or advance the build frontier — that is the continue/propose workflow.
- Draft the edit in conversation first; write only after the user confirms, one artifact at a time.
- Reconcile in both directions: an edit to a later artifact may require revising an earlier one.
- Use the artifact ids and paths reported by `openspec status` — never branch on hardcoded artifact names.
- Leave `skipped` artifacts untouched.
- If the request changes the change's *intent* rather than refining it, propose a new, unused change name instead.

#### openspec-archive-change
- Use the artifact graph (`openspec status --json`) to confirm completion; inform on warnings, do not block on them.
- If delta specs exist, always run the sync assessment and show the combined summary before archiving.
- Never archive while a spec sync is in flight — run the sync inline, verify the main specs, then move `changeRoot`.
- Preserve `.openspec.yaml` (it moves with the archived directory).
- Announce which change is selected; prompt when ambiguous.
- Never copy runtime context, operation guidance or artifact-rule text into output files.

#### openspec-sync-specs
- Read both the delta and the main spec before writing anything.
- Never copy a delta file into a main spec as-is — merge it into the Main Spec Format, with no delta operation headers.
- Preserve existing main-spec content the delta does not mention.
- The operation must be idempotent — running twice yields the same result.
- Use only `artifactPaths.specs.existingOutputPaths`; honor a caller-supplied subset and never widen it back.
- Stop before every main-spec write if the `openspec instructions` response is non-zero or invalid JSON.
- Show what you are changing as you go; ask when something is unclear.

#### openspec-explore
- Explore mode is for thinking — never write code or implement features. Point to `/opsx-propose` when the user is ready to build.
- Before any write-capable action, name the files and the proposed change, ask a direct yes/no, and wait for confirmation in a separate user message.
- Answers to design questions are never consent to write; silence is not acceptance.
- Never hand-scaffold `openspec/changes/` — always `openspec new change "<name>"`.
- Editing schemas, templates or `openspec/config.yaml` counts as a change, not as thinking.
- Do read files, run read-only commands, ground claims in the codebase, and draw diagrams liberally.
- Track decisions in the conversation as confirmed / proposed-default / open.
